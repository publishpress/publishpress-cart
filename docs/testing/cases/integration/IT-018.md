# Data Guard Reverts Local Edits To A Stripe Order Outside Sync Context

## Scenario

A Stripe-backed order keeps its authoritative state in Stripe-owned fields: status, payment status, the recorded transaction, and the refund log. When code outside a Stripe sync tries to overwrite those values, the data guard must restore the saved Stripe values so manual or accidental edits cannot diverge from the gateway. This protects against local code flipping an order to refunded or rewriting its charge without an actual Stripe event.

## Steps

1. Start with a Stripe order that has a recorded charge and one refund in its refund log (status paid, payment status paid).
2. Locally change the order: set it to refunded, change the recorded transaction, and replace the refund log with a different entry.
3. Run the data guard on the order without being inside a Stripe sync.

## Expected result

The Stripe-owned fields are restored to their saved values: the order is paid again, its recorded transaction is the original charge, and the refund log still holds the original refund. The local edits are discarded.

## Edge cases

- All four owned fields are checked together, including the list-valued refund log, to confirm structured data is preserved, not just simple values.
- Runs outside a sync, the boundary that distinguishes this preservation behavior from sync-driven writes.
