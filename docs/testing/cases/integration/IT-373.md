# Mailchimp REST client rejects invalid keys, handles PUT and 204, and syncs subscribers

## Scenario

Checkout-adjacent Mailchimp sync uses `ppcart_mailchimp_api_request()`, not
`\MailchimpMarketing\ApiClient`. Invalid credentials must fail before HTTP.
Member upsert must PUT JSON to the datacenter URL. Mailchimp DELETE 204 with an
empty body must succeed as an empty object, not a parse error.

## Steps

1. Leave `_ppcart_mailchimp_api` empty. Call `ppcart_mailchimp_api_request('lists')`.
2. Store `abc123-us1`. `pre_http_request` intercepts. PUT
   `lists/{id}/members/{hash}` with `email_address` / `status`.
3. Intercept DELETE of that member path; respond `204` with an empty body.
4. Respond `401` with a `detail` to a list fetch (`lists?count=100`).
5. Call `ppcart_add_remove_mailchimp_subscriber()` with action `subscribed`,
   groups `grp1,grp2`, tag `tag-55`, phone merge tag `PHONE`, and a
   `ppcart_mailchimp_merge_data` filter that adds `SOURCE`. All calls return 200.
6. Same call, but the member PUT returns `400`.
7. Same call with action `unsubscribed`.

## Expected result

1. `WP_Error` code `ppcart_mailchimp_invalid_api_key`. No HTTP.
2. Request URL is `https://us1.api.mailchimp.com/3.0/lists/{id}/members/{hash}`,
   method `PUT`, JSON body includes `email_address` and `status`. Return is the
   mocked JSON object.
3. Return is an empty `stdClass`, not `WP_Error`.
4. `WP_Error` `ppcart_mailchimp_api_error` with the `detail` and
   `['status' => 401]`. The request carries the Basic auth header.
5. Three requests in order: PUT member (merge fields include the filter value
   and phone), PATCH member `interests` `{grp1: true, grp2: true}`, PATCH
   `lists/list123/segments/55` with `members_to_add`.
6. Only the PUT is sent. No group or tag call. No order log entry.
7. One DELETE to the member path.

## Edge cases

- A 204 with `''` body must not hit the invalid-JSON error path.
