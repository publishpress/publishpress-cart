# File-Load Registration Does Not Compute Translated Template Defaults

## Scenario

When `includes/email/ppcart-email-template-functions.php` is loaded, it immediately calls `ppcart_register_email_template_option_filters()` to wire up the `default_option_*` and `option_*` filters for every email option. Registration must stay cheap: it iterates the static option-name list from `ppcart_email_template_option_names()` and never builds the translated default strings, which would force gettext (`__()`) calls before WordPress is ready for translation. The translated defaults are only produced lazily, when a registered filter callback actually runs and calls `ppcart_email_template_option_defaults()` / `ppcart_email_templates()`.

## Steps

1. Load `ppcart-email-template-functions.php`, which runs `ppcart_register_email_template_option_filters()` at file scope.
2. The registrar loops over `ppcart_email_template_option_names()` (a static array of option keys plus alias keys) and registers `add_filter('default_option_' . $option, ...)` and `add_filter('option_' . $option, ...)` for each name.
3. Inspect the stubbed translation counter (`translation_calls`) captured by the test's WordPress stub context, which increments whenever a translation function would be invoked.

## Expected result

- After file-load registration, `translation_calls` is exactly `0`: no template default (e.g. the translated `_ppcart_email_completed_subject` string `Your order from {site_name} is complete!`) is computed during registration.
- Translation work is deferred until a `default_option_*` / `option_*` filter callback actually fires and resolves a default.

## Edge cases

- A template default that embeds gettext (such as the body built by `ppcart_get_editable_order_details_email_body()`) must still not trigger translation at registration time, only when the option value is first resolved.
