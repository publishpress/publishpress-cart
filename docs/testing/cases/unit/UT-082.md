# Static Email Option Names Cover All Core Defaults And Aliases

## Scenario

`ppcart_email_template_option_names()` returns the static list of canonical option keys used to register filters cheaply (without translating template defaults). That static list must stay in sync with the two dynamic sources of truth: every option key produced by `ppcart_email_template_option_defaults()` and every semantic alias key in `ppcart_email_template_alias_options()`. This case guards against a default or alias being added without also being added to the static names list (which would leave its `default_option_*` / `option_*` filters unregistered).

## Steps

1. Collect `array_keys(ppcart_email_template_option_defaults())` (e.g. `_ppcart_email_from_name`, `_ppcart_email_completed_subject`, ...).
2. Collect `array_keys(ppcart_email_template_alias_options())` (the `_ppcart_email_past_due_*` semantic alias keys).
3. Compute `array_diff` of the merged set against `ppcart_email_template_option_names()`.

## Expected result

- The diff is an empty array `array()`: every defaults key and every alias key is present in `ppcart_email_template_option_names()`.

## Edge cases

- A newly added template field default or a new legacy alias must be reflected in the static names list, otherwise this diff becomes non-empty and the case fails.
