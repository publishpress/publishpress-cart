# Sensitive-option registry recognizes credential keys and ignores non-secrets

## Scenario

Security case. The encryption and redaction layer only protects option keys it knows to be secrets, so the registry behind `ppcart_is_sensitive_option()` must positively identify credential keys (Stripe secret key, Mailchimp API key, Drip API key) and must not misclassify benign settings (currency). A gap here would leave a real credential stored as plaintext or needlessly obscure a harmless option.

## Steps

1. Call `ppcart_is_sensitive_option('_ppcart_stripe_test_sk')`.
2. Call `ppcart_is_sensitive_option('_ppcart_stripe_test_webhook_secret')`.
3. Call `ppcart_is_sensitive_option('_ppcart_mailchimp_api')`.
4. Call `ppcart_is_sensitive_option('_ppcart_drip_api_key')`.
5. Call `ppcart_is_sensitive_option('_ppcart_currency')`.
6. Call `ppcart_is_sensitive_option('_ppcart_encrypt_secrets')`.
7. Call `ppcart_is_sensitive_option('_sc_mailchimp_api')`.
8. With the database flag on, call `PPCart_Secrets::filter_pre_update_any_option('1', '_ppcart_encrypt_secrets', '0')`.
9. Replace the stored flag with an undecryptable `ppenc1:` value and read enablement helpers.

## Expected result

- `_ppcart_stripe_test_sk`, `_ppcart_stripe_test_webhook_secret`, `_ppcart_mailchimp_api`, and `_ppcart_drip_api_key` each return `true` (recognized as sensitive credentials).
- `_ppcart_currency` and `_ppcart_encrypt_secrets` return `false` (normal settings that must stay readable plaintext).
- Leftover `_sc_mailchimp_api` / `_sc_currency` return `false` in Cart first-party.
- Saving the encryption control flag stores plaintext `'1'`, not a `ppenc1:` blob.
- An undecryptable `ppenc1:` flag does not enable encryption (`disabled` control source).

## Edge cases

- A non-registered key (e.g. a future integration's credential) returns `false` until it is added to the registry, which is the signal that it is not yet protected.
