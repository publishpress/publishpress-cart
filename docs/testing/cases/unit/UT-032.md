# Debug Log View Handler Returns Early Off The Settings Page

## Scenario

Security/access-control case. The debug log `view_log_request()` handler must only ever act on the plugin's own settings screen. When a request carries a log action (`ppcart_view_log`) but targets some other admin page, the handler must bail out before performing any capability check, nonce verification, or output. This prevents the log viewer from being triggered from unrelated admin contexts.

## Steps

1. Simulate a request where `$_REQUEST['page']` is `other-page` and `$_REQUEST['ppcart_view_log']` is `1`.
2. Simulate the current user lacking the `manage_options` capability.
3. Call `PPCart_Debug_Logger::view_log_request()`.

## Expected result

The handler returns early without acting: `wp_die()` is never invoked (no denial output is produced) and the nonce check (`check_admin_referer`) is never reached. The page-slug guard short-circuits before any capability or nonce logic runs.

## Edge cases

- A foreign page slug combined with a valid-looking log action must not leak the log or even reach the capability gate — the page guard alone stops it.
