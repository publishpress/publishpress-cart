# Registered Post Status Labels Are Used Before Fallback

## Scenario

`PPCart_Status_Labels::get()` resolves a human-readable label for an order or subscription status key. When WordPress already has a registered post status object for that key, the label registered with WordPress must win over the plugin's hard-coded fallback table. This lets translated or customized status labels flow through instead of the built-in English defaults.

## Steps

1. Register a WordPress post status object for the key `paid` whose `label` property is `Paid translated` (simulated via the stubbed `get_post_status_object()`).
2. Call `PPCart_Status_Labels::get('paid')`.

## Expected result

The method returns `Paid translated` (the label from the registered status object), not the plugin fallback string `Paid` that the internal table would otherwise produce for `paid`.

## Edge cases

- If the registered status object exists but has no `label` property, resolution should fall through to the fallback table rather than returning an empty or broken value.
