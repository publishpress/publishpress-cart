# New User Welcome — enabled sends

## Scenario

Automated by `tests/playwright/admin/email-020-registration-enabled-sends.spec.ts`. With **New User
Welcome** turned on from the Emails settings tab, creating a customer account delivers the welcome
email. This type never reaches `ppcart_notification_send()` — the path is `ppcart_create_user()` →
`ppcart_new_user_notification()` — so the trigger is `create_user`, not an order status change.

## Steps

1. Skip unless admin credentials and the email fixture ids (`composer test:admin:setup`) are present.
2. Open `<site>/wp-admin/admin.php?page=ppcart-settings#emails` and confirm `#content_tab_emails`.
3. Open the `emailtemplate_registration` Manage modal.
4. Turn `_ppcart_email_registration_enable` on and force `_ppcart_use_wp_notification` off, both by
   clicking their `label[for=...]` elements — the inputs are `display: none`, so `check()` cannot be
   used. When the WP-notification option is on, core's `wp_new_user_notification()` sends and the
   plugin template never runs, so both boxes must be set before the single shared save.
5. Save from inside the modal and wait for the `settings-updated=true` redirect.
6. Assert the "New User Welcome" row status dot renders `is-enabled`.
7. Empty the Mailpit mailbox.
8. POST the fixtures trigger `create_user` for the seeded order with a unique `@example.invalid`
   recipient.

## Expected result

1. A Mailpit message addressed to that recipient arrives within the wait window.
2. Its subject is not empty.

## Edge cases

- Each run creates a real WordPress user, so the address must be unique; a repeat would send
  `ppcart_create_user()` down its "user already exists" branch, which sends nothing.
- `setEmailEnabled()` alone cannot drive this type — the companion `_ppcart_use_wp_notification`
  option means the spec builds the modal interaction itself.
