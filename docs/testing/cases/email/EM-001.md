# Pending — enabled sends

## Scenario

Automated by `tests/playwright/admin/email-001-pending-enabled-sends.spec.ts`. With **Order Received
Confirmation** turned on from the Emails settings tab, an order moving to status `pending` delivers
the customer email. The toggle is driven through the real settings UI, so the case proves the
settings page — not just the option value — controls delivery.

## Steps

1. Skip unless admin credentials and the email fixture ids (`composer test:admin:setup`) are present.
2. Open `<site>/wp-admin/admin.php?page=ppcart-settings#emails`; the `#emails` hash picks the tab
   before the `ppcartSettingsActiveTab` localStorage fallback. Assert `#content_tab_emails` is visible.
3. Click `[data-testid="ppcart-admin-email-emailtemplate-pending-manage"]` and wait for the modal to
   carry `is-open`.
4. Turn `_ppcart_email_pending_enable` on by clicking `label[for="_ppcart_email_pending_enable"]` —
   the input is `display: none`, so Playwright's `check()` cannot reach it even with `force`.
5. Save with the in-modal save button and wait for the `settings-updated=true` redirect.
6. Assert the "Order Received Confirmation" row status dot renders `is-enabled`, i.e. the save
   persisted, before anything is fired.
7. Empty the Mailpit mailbox.
8. POST the fixtures trigger `order_status` for the seeded order with status `pending` and a unique
   `@example.invalid` recipient.

## Expected result

1. A Mailpit message addressed to that recipient arrives within the wait window.
2. Its subject is not empty.

## Edge cases

- The spec runs serially: every settings tab shares one `<form>` posting to `options.php`, so a
  parallel save would rewrite the option under test mid-run.
- The recipient is unique per worker and per call, so concurrent runs cannot match each other's mail.
