# Pending — disabled does not send

## Scenario

Automated by `tests/playwright/admin/email-002-pending-disabled-does-not-send.spec.ts`. The mirror of
EM-001: with **Order Received Confirmation** turned off from the Emails settings tab, the same
`pending` order transition must deliver nothing.

## Steps

1. Skip unless admin credentials and the email fixture ids (`composer test:admin:setup`) are present.
2. Open `<site>/wp-admin/admin.php?page=ppcart-settings#emails` and confirm `#content_tab_emails`.
3. Open the Order Received Confirmation Manage modal.
4. Turn `_ppcart_email_pending_enable` off by clicking `label[for="_ppcart_email_pending_enable"]`,
   because the input is `display: none` and `check()`/`uncheck()` cannot act on it.
5. Save from inside the modal and wait for the `settings-updated=true` redirect.
6. Assert the row status dot renders `is-disabled` — the persisted "off" state is confirmed before
   any trigger fires.
7. Empty the Mailpit mailbox.
8. POST the fixtures trigger `order_status` for the seeded order with status `pending` and a unique
   `@example.invalid` recipient.

## Expected result

1. No Mailpit message addressed to that recipient arrives during the full quiet window. The helper
   always elapses the whole window rather than returning early, so merely slow mail cannot pass.

## Edge cases

- The trigger helper throws unless the endpoint reports success, so "nothing arrived" cannot be
  explained away by the trigger never having run.
- Asserting persistence in step 6 is what stops a silently failed save from turning this into a false
  green.
