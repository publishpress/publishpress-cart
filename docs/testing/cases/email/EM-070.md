# Email enable toggles persist across a reload

## Scenario

Automated by `tests/playwright/admin/email-070-toggles-persist.spec.ts`. Pure settings coverage, no
mail involved: every one of the seven free email types must save and survive a page reload in **both**
directions. All fourteen combinations are exercised in one serial loop.

## Steps

1. Skip unless admin credentials and the email fixture ids (`composer test:admin:setup`) are present.
2. For each of the seven types in `EMAIL_TYPES`, and for `enabled` of `true` then `false`:
   1. Open the Emails tab via the `#emails` hash, open that type's Manage modal, and set its enable
      option to the target state by clicking `label[for=...]` — the inputs are `display: none`, so
      `check()`/`uncheck()` cannot be used.
   2. Save from inside the modal and wait for the `settings-updated=true` redirect.
   3. Re-open the Emails tab as a fresh request, so the next assertions read what `get_option()`
      returns rather than the DOM the test just clicked into shape.
   4. Assert the row status dot matches the target state.
   5. Re-open the Manage modal and assert the checkbox itself matches the target state — the dot and
      the control render from the same option but by different code paths.

## Expected result

1. All fourteen on/off round trips persist: each type's row dot and modal checkbox both report the
   state that was saved.

## Edge cases

- The enable flags have no registered default, so a save that dropped the value entirely would still
  leave a fresh page rendering "off". Only the on → reload → on leg catches that, which is why both
  directions are looped rather than just the off one.
- Fourteen full settings saves make this the longest-running spec in the suite; it runs serially with
  an extended timeout.
