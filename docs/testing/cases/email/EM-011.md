# Purchase Confirmation — disabled does not send

## Scenario

Automated by `tests/playwright/admin/email-011-purchase-disabled-does-not-send.spec.ts`. With
**Purchase Confirmation** turned off from the Emails settings tab, a `paid` order transition must
deliver nothing. This is the direction that regressed before `a559433f`:
`_ppcart_email_confirmation_enable` read `0`, `ppcart_notification_send()` returned before
`wp_mail()`, and the customer never learned their purchase went through.

## Steps

1. Skip unless admin credentials and the email fixture ids (`composer test:admin:setup`) are present.
2. Open the Emails tab via the `#emails` hash and confirm `#content_tab_emails`.
3. Open the Purchase Confirmation Manage modal (`emailtemplate_purchase`, not `confirmation`).
4. Turn `_ppcart_email_confirmation_enable` off by clicking its `label[for=...]`, because the input is
   `display: none` and `uncheck()` cannot act on it.
5. Save from inside the modal and wait for the `settings-updated=true` redirect.
6. Assert the row status dot renders `is-disabled` before any trigger fires.
7. Empty the Mailpit mailbox.
8. POST the fixtures trigger `order_status` for the seeded order with status `paid` and a unique
   `@example.invalid` recipient.

## Expected result

1. No Mailpit message addressed to that recipient arrives during the full quiet window, which is
   always elapsed in full so slow mail cannot produce a false green.

## Edge cases

- The trigger helper throws unless the endpoint reports success, so a never-fired trigger cannot
  masquerade as a correctly suppressed email.
- Options persist as the string `"0"` rather than being absent, so a persisted "off" is
  distinguishable from never-configured.
